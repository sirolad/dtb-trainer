# DTB C1 interactive quiz UI design

Date: 2026-09-28

## Purpose and scope

The existing DTB C1 Prüfungstrainer plugin (version 0.1.6) can generate a clickable native quiz, but its widget does not deliver selected answers to the trainer. A live three-question test ended with a score and per-answer explanations but no weakness analysis or expandable error cards. The user wants one clickable quiz surface that retains answer state and finishes with the promised diagnosis. This project delivers that flow for multiple-choice mini-tests and weakness tests. It does not add accounts, cross-session progress, audio playback, or a custom GPT integration.

## User experience

The user asks the existing plugin for a mini-test or weakness test. ChatGPT calls a plugin tool with generated questions. The returned component shows one question at a time, four clickable options, progress, and an optional hint that does not reveal the answer. The user can select an option and advance. In practice mode, a concise explanation may appear after selection. In exam mode, no correctness feedback appears before completion. After the last question, the same component shows the actual score, an expandable card for each error, and no more than two provisional observations about weaknesses. Each error card contains the selected and correct options, explanations, the decisive short quote formatted as inline code, a category, and a new transfer prompt. The result can be reviewed without another chat message.

The writing comparison instructions from version 0.1.6 remain in place. This project does not convert that view into a separate MCP component.

## Approach

Add a small stateless MCP server with a `start_quiz` tool and a linked MCP Apps UI resource. It accepts validated quiz data generated by ChatGPT and returns a component that owns answer selection and scoring in the iframe. The server does not store attempts. This design avoids paying for a database and prevents the known failure in which a native quiz's private click state cannot be inspected by the assistant. A standalone webpage would not deliver the result inside the plugin; further prompt edits cannot guarantee local click state is available. The MCP UI is therefore the required component.

Host the MCP endpoint at a public HTTPS URL selected during deployment. Hosting can have a cost and depends on an available deployment account. Do not embed credentials or a temporary tunnel URL in the plugin package. Until the endpoint is reachable and tested, do not publish a plugin release claiming the UI works.

## Components and interfaces

1. **Quiz data schema:** `title`, `mode` (`practice`, `exam`, or `diagnostic`), and 1 to 20 questions. Each question has a stable id, area, category, question text, four unique A/B/C/D options, one correct option, explanations for the correct option and each distractor, optional non-answer hint, and a short exact `evidenceQuote` where applicable. Text is untrusted data and must be rendered as text, not HTML.
2. **MCP tool:** `start_quiz` validates input and returns a structured result with quiz data and UI metadata pointing to `ui://dtb-c1/quiz.html`. Reject malformed questions with a clear tool error. It performs no scoring or persistence.
3. **UI resource:** A self-contained responsive component implements the question state machine: unanswered, answered, advanced, complete. It records selected option ids in local component state, computes score from the validated key, and renders results. It does not rely on ChatGPT seeing clicks. Escape displayed content and render `evidenceQuote` with a semantic `<code>` element.
4. **Plugin package:** Add a portable `mcp.json` reference to the deployed server; retain the existing skill and exam materials. Update the skill to route multiple-choice diagnostic tests to `start_quiz`, avoid the native widget for diagnoses, and describe the fallback when the tool is unavailable. Increment the plugin version. Preserve manifest identity, metadata, and prompts.

## Diagnosis rules

Always count actual selected answers. Group errors by category and cite question ids as evidence. Limit the result to two actionable observations. With one question in a category, label the conclusion provisional rather than treating one mistake as an established weakness. If there are no errors, say that no weakness was demonstrated in this quiz. A three-question test must not claim a stable skill profile. Suggested follow-up questions can target errors, but cannot be presented as already answered.

## Error handling and accessibility

The server rejects duplicate ids, missing feedback, invalid answer keys, absent categories, empty prompts, and question counts outside the limit. The UI never silently substitutes missing answers. If the iframe reloads, it may restart the attempt; show a clear restart state rather than inventing results. Keyboard focus, visible focus styles, labelled buttons, sufficient contrast, and small-screen stacking are required. A client without MCP UI support gets a readable tool result; if the tool is unavailable, the skill asks one question at a time in chat and scores the chat replies.

## Verification and release

Test schema rejection and scoring with wrong, correct, mixed, and unanswered attempts. Test provisional diagnosis with one error per category, no errors, and repeated errors. Check that exam mode hides feedback until completion, literal quotes are safely rendered, and keyboard/mobile interaction works. Run the MCP server locally with an inspector, then connect the deployed HTTPS endpoint in ChatGPT and complete a live quiz through the final result. Only after the live result displays score, error cards, and analysis should the existing plugin be updated and read back. Roll back the plugin release if the new tool fails in the live flow.

## Delivery constraints

The current workspace is a scratch export of the plugin, not a Git repository. Preserve the design in the user's Library. Production deployment needs a reachable HTTPS host and any required account authorization. The user has approved the architecture, but the written spec and implementation plan are separate review stages before coding under the brainstorming workflow.
